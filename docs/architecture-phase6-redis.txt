WHY REDIS

Repeated search requests do not always need to execute
the same Elasticsearch query again.

Redis can reduce:

- Elasticsearch query load
- CPU usage
- repeated aggregation work
- response latency for hot searches


CURRENT CACHED ENDPOINTS

/api/search/advanced

/api/search/facets


NOT CACHED

Fuzzy search

Autocomplete

These are intentionally left uncached for now because
their query diversity is usually much higher.


CACHE CONSISTENCY

When Kafka reports a product change:

1. Consumer updates Elasticsearch.
2. Consumer clears search cache.
3. Next request misses Redis.
4. Fresh Elasticsearch result is returned.
5. Fresh result is stored in Redis.


PRODUCTION NOTE

This learning implementation clears search:* keys.

For very large Redis deployments, avoid broad KEYS-based
cache invalidation and use strategies such as:

- versioned cache namespaces
- targeted cache tags
- SCAN
- event-specific invalidation
- short TTLs
